## 운영 결정 요약

운영자가 서로 다른 업무 3~4건을 한 번에 맡기면, AI-Office가 접수 순서를 보관하고 실행 가능한 업무를 한 건씩 처리한다. 운영자는 다음 건을 시작시키기 위해 돌아올 필요가 없다. 일이 끝나면 한 화면에서 각 결과를 열고, 본인 결정이 필요한 건만 이어서 처리한다.

| 결정할 사항 | 2.0 권고안 |
|---|---|
| 무엇을 한 건으로 보는가 | 운영자가 작성한 업무 항목 하나. 첨부·완료 기준·발송 권한은 그 항목에만 속한다. 네 건을 한 개의 긴 프롬프트로 합치지 않는다. |
| 무엇을 순차 처리하는가 | 같은 작업 공간의 일반 업무는 한 번에 한 건. 업무 내부 직원은 기존 한도 안에서 독립 단계를 병렬 수행한다. |
| 앞 업무가 멈추면 어떻게 하는가 | 운영자 답변·자료·외부 결과 확인을 기다리는 건은 실행 자리를 반납한다. 뒤의 독립 업무는 진행하고, 선행 결과가 필요한 업무는 이유를 표시해 보류한다. |
| 어디에서 AI를 쓰는가 | 담당 업무의 판별·판단·작성·필요한 검토에 사용한다. 묶음 접수, 대기 순번, 상태 조회, 보고 카드 조립은 저장된 정보로 처리한다. |
| 무엇을 성공으로 보는가 | 4건 접수 후 누락·이중 실행 없이 건별 결과 4개가 설명되고, 보고 카드 하나에서 산출물 또는 미완료 사유를 확인할 수 있다. |

**2.0 반영 범위.** 운영자는 PC·태블릿·휴대폰에서 같은 업무 번호로 접수, 답변, 결과 확인을 이어간다. 업무 처리 이력 내보내기, 발송 결과 대조함, 대기시간 누적 알림을 정식 범위에 포함한다. 이력은 첫 파일럿부터 제공하고, 대조함은 외부 발송 파일럿 전에 연다. 알림은 첫날부터 대기시간을 기록한 뒤 운영 표본을 확보하면 활성화한다.

**업무 봇 사용 가이드**를 내부 파일럿의 필수 페이지로 제작한다. 운영자가 업무 이름으로 적합한 봇을 찾고, 필요한 자료·처리 순서·결과 예시를 읽은 뒤 명령을 작성할 수 있어야 한다.

핵심 성과는 **운영자가 기다리며 재지시하는 횟수와 불필요한 AI 호출을 줄이는 것**이다. 오래 걸리는 네 건을 순차 처리하면 맨 뒤 업무는 앞 업무들의 실제 작업 시간만큼 기다린다. 전체 완료 시간의 단축 여부는 처리량·품질·사용량을 함께 재어 판단한다.

## 1. Read — 현재 어떻게 일하는가

### 한 건의 요청이 최종 보고가 되기까지

| 단계 | 현재 버전에서 확인한 동작 | 운영상 의미 |
|---|---|---|
| ① 지시 접수 | 대시보드 지시창이 한 개의 요청을 제출한다. 서버가 새 업무·추가 지시·중지·재개·예약 등을 판별한다. 같은 문구의 동시 제출 차단은 판별 중에만 적용된다. | 요청 단위의 처리가 기본이다. 다른 업무가 끝나야 새 요청이 가능하다는 전역 잠금은 확인되지 않았다. |
| ② 경로 선택 | 빠른 조회·간단한 수정, 등록된 고정 절차, 일반 계획 경로가 있다. 일반 경로에서는 필요에 따라 계획과 분담을 만든다. 회사 스냅샷에는 고정 절차 6개와 예약 4건이 있다. | 매번 모든 직원을 모아 계획을 다시 짜는 구조가 아니다. 이미 있는 빠른 경로는 보존할 가치가 있다. |
| ③ 직원 실행 | 실행기의 기본 CLI 동시 실행 한도는 4개다. 이를 넘는 실행은 대기한다. 업무를 지휘하는 상위 실행은 이 카운트에서 제외된다. 준비된 독립 단계는 병렬로 수행한다. | 네 개의 직원 실행을 조절하는 것과 운영자 업무 네 건의 순서를 보장하는 것은 서로 다른 문제다. |
| ④ 점검·재작업 | 계획 수정 최대 3회, 진행 점검 최대 12회, 도구 부족 재계획 최대 2회 등 경로별 제한이 있다. 일반 최종 검토는 재작업 1회, 외부 작업·전문 검토 경로는 2회를 기준으로 마지막 검토로 넘어간다. 승인된 검토 결과를 재사용하는 경로도 있다. | 기존에도 반복 방지 장치가 있다. 각각의 상한을 지켜도 판별·분담·재계획·검토가 겹치면 한 업무의 호출은 늘어난다. |
| ⑤ 전달·복구 | 일반 전달 경로는 건별 보고 저장 → 최종 산출물 수집 → 업무 완료 기록 → 전달 이벤트 순서다. 산출물 수집 실패 시 질문할 수 있다. 서버 재시작 시 예전 일반 queued는 stopped, 실행 중이던 건은 추적 중단으로 정리한다. 감시 업무는 별도 복구 규칙을 쓴다. | 보고 파일 존재, 실행 종료, 사용자에게 결과 전달 완료가 서로 다른 시점이다. 기존 직원 대기열만으로는 운영자에게 약속한 접수 순서를 복구할 수 없다. |

**실제 자료 대조.** 11월 24일 회사 백업의 AI 브리핑은 ‘자료 수집 → HTML 작성’, 운영 평가는 ‘업무 기록 검토 → 개선 노트’의 두 단계로 계획됐고 각각 건별 보고가 있었다. 이 두 표본에서 단계 수와 산출물 연결을 확인했다. 운영자의 실제 대기시간, 전체 호출 수, 공급자별 토큰 원장은 이 자료로 확정할 수 없다.

## 2. Evaluate — 어디서 막히고 사용량이 늘어날 수 있는가

아래는 코드 경로로 확인한 위험이다. 특정 병목이 운영 시간의 몇 퍼센트를 차지하는지, 무한 루프가 실제로 발생했는지는 별도 실측 대상이다.

| 지점 | 발생 조건과 영향 | 2.0 판단 |
|---|---|---|
| 접수 전 의도 판별 | 기존 판별기는 기본 최대 15초 대기할 수 있다. 네 건 모두를 먼저 판별해야 접수된다면 대기 업무에도 AI 비용이 들고 응답 유실 후 재제출될 수 있다. | 저장 성공을 먼저 알려 준다. 명시적 업무 항목의 내용 판별은 실행 차례에 한 번 수행한다. |
| 선두의 장기 작업 | 대형 수집·장문 보고 중 뒤 업무가 밀린다. 로그인이나 승인까지 실행 자리를 차지하면 담당자 퇴근 후 전체가 멈춘다. | 실행 중인 정상 장기 업무의 순서를 지킨다. 사람 대기·실패·예산 보류는 즉시 자리를 반환하고 다음 건을 선택한다. |
| 부모·직원 간 교착 | 업무 한 건 제한을 기존 직원 한도에 적용하면 부모가 직원을 기다리거나 내부 병렬 단계가 모두 직렬화된다. | 상위 업무 자리와 직원 자리를 별도로 센다. 입력 대기·상시 감시 부모도 상위 업무 자리를 점유하지 않는다. |
| 검토와 형식 오류의 왕복 | 최종 검토의 재작업 한도에 도달해도 외부 작업 형식 검사 오류가 남으면 다시 reject가 되는 경로가 있다. 예산 점검은 있으나 같은 원인으로 시간을 쓸 수 있다. | 같은 입력·같은 오류·산출물 변화 없음이 재확인되면 해당 업무를 보류한다. 외부 전송 조건 미충족은 자동 승인으로 해소하지 않는다. |
| 계측 누락·중복 합산 | 업무 예산 카운터는 오케스트레이터의 실행 호출을 센다. 접수 의도 판별은 별도 CLI 경로다. 자식 사용량을 부모에 합치는 경로가 있고, 일별 합산에서는 미보고 토큰이 합계에 0만큼 더해질 수 있다. | 공급자 호출별로 한 번만 집계한다. ‘측정된 합계’와 ‘미보고 건수’를 함께 표시한다. 호출 횟수는 토큰 총량과 별개다. |
| 보고·재접속·장애 복구 | 완료 이벤트, 화면 재접속, 보고 저장 재시도가 다시 업무 시작으로 이어지면 결과를 낸 후에도 호출이 반복될 수 있다. | 화면 갱신은 조회로만 처리한다. 결과가 있으면 보고만 복구한다. 외부 발송 결과가 불확실하면 증표를 대조할 때까지 수동 확인한다. |

### 호출·시간·토큰을 구분해야 하는 이유

확인한 회사 설정은 **업무당 240회·180분**이다. 일반 업무는 둘 중 사용 비율이 높은 쪽이 80%에 이르면 계속할지 묻고, 계속하면 예산이 늘어나는 경로가 있다. 무인 실행은 해당 예산 점검에서 100%에 이르면 이번 회차를 중단한다. 감시 사용량 이상 알림은 평소 대비 **호출 수**를 기준으로 한다.

같은 설정을 네 업무에 따로 부여하면 초기 호출 예산의 명목 합계는 **240 × 4 = 960회**다. 이는 실제 소비량·예상치·절대 상한을 뜻하지 않는다. 승인 연장, 예산 점검 시점 및 별도 판별 경로까지 고려해야 한다. 네 업무를 한꺼번에 저장하는 것만으로는 사용량이 줄지 않는다. **아직 차례가 오지 않은 업무의 AI 호출을 0으로 유지하고, 이미 끝낸 일을 재요청하지 않는 것**이 비용 통제의 출발점이다.

## 3. Plan — 운영자가 맡긴 네 건을 처리하는 규칙

### 3.1 접수와 순번

1. ‘새 업무’에서 항목을 하나씩 추가한다. 항목마다 요청 원문·첨부·완료 기준을 붙이고, 필요하면 같은 묶음의 앞선 항목을 선행 업무로 지정한다. 항목 내 줄바꿈은 그대로 보존한다. 자연어 한 문장을 AI로 자동 분할하는 기능은 후속 검토 대상으로 둔다.
2. 제출 시 전체를 저장한 뒤 묶음 번호, 건별 번호, 제출 순서를 돌려준다. 전체 저장에 실패하면 접수 완료로 표시하지 않는다. 응답이 유실되어 같은 제출을 다시 보내도 같은 번호를 돌려준다. 제목이 같은 새 제출은 별도 업무가 될 수 있다.
3. 실행 차례는 같은 작업 공간에서 **실행 가능한 건 중 가장 먼저 접수된 건**이다. 같은 시각이면 저장된 순번을 쓴다. 이미 실행 중인 업무를 선점하지 않는다. 실행 중 추가 접수도 가능하다.
4. 보류 건에 자료가 들어오면 같은 업무 번호로 재개한다. 이미 실행 중인 건은 끝까지 진행하고, 빈 자리가 생기면 보완된 건의 최초 순번을 적용한다. 동일 답장을 반복해도 재개는 한 번이다. 이미 사람이 중지한 건은 명시적으로 재개하기 전까지 멈춘 상태를 유지한다.
5. 유한 예약 업무는 기존 예약 규칙이 이번 회차를 허용한 시점에 한 번만 접수한다. 예약 시각과 실제 시작 시각을 구별한다. 놓친 과거 예약 몰아 실행, 같은 회차 재등록은 기존처럼 막는다. 상시 감시는 주기와 커서를 유지하고, 새 자료에서 파생된 유한 후속 업무만 같은 대기열을 사용한다.

### 3.2 업무 네 건으로 보는 하루

| 접수 순서 | 운영자 요청 | 처리 및 화면 표시 |
|---|---|---|
| A | 유니타로 금~목 회신 현황 집계 | 집계표를 저장하고 건별 결과에 연결한다. |
| B | A 집계를 반영해 주간보고 초안 작성 | A의 확정 집계만 읽는다. A가 보류되면 ‘A 집계 대기’가 되며 새 조사나 재질문을 반복하지 않는다. |
| C | 상담사 프로필 검수 목록 정리 | 담당자 명단이 없으면 ‘명단 첨부 필요’로 남기고 다음 건에 자리를 넘긴다. |
| D | 배너 이월대기 현황 정리 | C와 독립적이므로 명단을 기다리는 동안 완료한다. |

A·B·D가 끝나면 묶음 보고는 **완료 3 / 확인 필요 1**이며, C의 요청 자료와 답변 위치가 보인다. 명단을 첨부하면 C만 재개되고 같은 보고가 **완료 4 / 4**로 바뀐다. A~D 산출물은 건별로 열 수 있다. 운영자가 C를 취소하면 최종 집계는 **완료 3 / 취소 1**이며 취소한 작업을 다시 깨우지 않는다.

### 3.3 예외 상태와 보고의 종료 조건

| 상태 | 실행 자리 | 다시 움직이는 조건 |
|---|---|---|
| 대기·선행 업무 대기 | 사용 안 함 | 접수 순번 도래 또는 선행 업무의 결과 확정. 앞선 항목만 선행으로 선택해 순환을 막는다. |
| 진행 중 | 해당 업무 1건 | 완료 증거 저장, 확인 필요, 실패 또는 중지 중 하나로 이동한다. |
| 자료·승인·예산 확인 필요 | 반납 | 새 자료, 해당 업무의 승인, 명시적 예산 확대 등 실제 상태 변화가 있을 때만 재개한다. |
| 보고 반영 대기 | 본 작업 자리 반납 | 건별 확정 결과로 카드 갱신만 재시도한다. 결과 파일 수집이 끝나지 않았다면 ‘완료’로 세지 않는다. |
| 완료·실패·취소 | 반납 | 실패는 증거와 원인을 남기고 자동 종료한다. 재처리는 운영자가 요청한 새 시도로 기록한다. |

묶음 보고의 한 행은 건별 번호·제목·상태·결과 한 줄·산출물 또는 미처리 사유·다음 행동으로 구성한다. 묶음의 모든 행이 끝나거나 사람의 결정을 기다리면 현 시점의 집계를 확정한다. 같은 카드에서 갱신하며 재개·결과 확정 이력을 남긴다. 모든 행의 상태별 건수 합계는 언제나 최초 접수 건수와 일치해야 한다.

## 4. 토큰과 반복 실행에 대한 운영 정책

### 4.1 AI 호출을 허용하는 시점

| 동작 | AI 사용 정책 |
|---|---|
| 접수증 발행·대기 순번·화면 갱신·완료 알림·묶음 보고 | 추가 AI 호출 0회. 저장된 건별 정보로 표시한다. |
| 실행 차례가 온 일반 업무 | 필요한 판별 결과를 업무에 저장한다. 검토·재시작·새로고침에서 같은 판별을 재요청하지 않는다. |
| 고정 절차·간단한 조회·수정 | 기존 빠른 경로와 사전 점검을 우선 사용한다. 원문이나 실행 권한이 달라지면 관련 판단만 갱신한다. |
| 자료 전달·검토 | 직원에게 해당 단계의 목표·필요한 원문 또는 파일 위치·완료 기준·직전 수정 사유만 준다. 같은 묶음의 다른 대화 전체와 로그 전체를 매번 첨부하지 않는다. 원문 대조가 필요한 검토자는 허용된 원문을 열 수 있어야 한다. |
| 재개·재시도 | 새 자료가 영향을 준 단계와 그 결과를 쓰는 후속 단계만 재개한다. 실패한 외부 발송이나 게시의 결과가 불명확하면 자동 재전송 0회다. |

### 4.2 예산을 적용하는 방법

- **업무 예산.** 호출 수, 실제 활동 시간, 공급자가 보고한 입력·출력 토큰을 분리한다. 사람 답변·대기열 대기 시간은 대기시간 지표에 기록한다. 예약·감시·권한 판단의 기존 보호 조건을 유지한다.
- **묶음 예산.** 동시 접수가 자동으로 4배 지출 승인이 되지 않도록 묶음 전체의 호출·토큰 허용량을 별도로 설정한다. 업무별 한도와 묶음 한도 중 먼저 닿는 쪽을 적용한다. 최초 파일럿은 기존 업무 1건의 호출 예산을 묶음 전체의 안전 상한으로 삼는 보수안이며, 정상 4건에 부족하면 운영자가 예상 잔여량을 보고 확대한다. 240회는 공급자 총 토큰 보장이 아니다.
- **토큰 기준의 확정.** 동일 자료·동일 모델·동일 완료 기준의 대표 단건을 먼저 측정한다. 네 건에 필요한 단계별 입력·출력과 관측 편차로 파일럿 토큰 한도를 정한다. 측정 전에 절감률이나 고정 토큰 수를 운영 확정값으로 쓰지 않는다. 입력·출력과 캐시 읽기·생성은 공급자 정의에 맞춰 표시하고 중복 합산을 피한다.
- **호출 직전 점검.** 상위 업무의 판별, 실행, 검토, 재시도까지 하나의 묶음에 귀속한다. 병렬 직원 호출은 시작 전에 각각 잔량을 예약하고 종료 후 실측값으로 정산한다. 부모 합계와 자식 개별 호출은 한쪽만 합산한다. 판별처럼 기존 업무 예산 밖에서 수행된 호출도 계측 대상이다.
- **중단 기준 제안.** 묶음 허용량의 80%에서 한 번 알리고, 다음 호출이 잔량을 초과할 것으로 판단되면 새 호출을 보류한다. 100%에서는 새 AI 호출을 시작하지 않는다. 실행 중인 호출의 사용량이 늦게 들어오면 실제 초과분을 그대로 표시한다. 공급자가 호출당 상한을 강제하지 못하는 환경은 ‘신규 호출 차단’과 ‘실제 토큰 상한 보장’을 구분해 표시한다.
- **미보고 사용량.** ‘확인된 입력·출력 / 미보고 호출 수 / 측정 가능 비율’을 함께 표시한다. 실제값이 없으면 0으로 정산하지 않는다. 공급자별 보수적인 예약량으로 관리하고 신뢰할 추정도 없으면 추가 무인 호출을 보류한다. 한도 확대는 해당 묶음의 추가 허용량과 사유를 기록한다. 업무별 승인과 묶음 예산 승인은 서로 대체되지 않는다.
- **보류 범위.** 한 업무의 한도만 닿으면 다른 독립 업무는 계속할 수 있다. 묶음 한도가 닿으면 같은 묶음의 AI 실행을 모두 보류한다. 저장된 결과 열람·보고 갱신은 계속 가능하다. 별도 예산이 있는 다음 묶음은 실행할 수 있다.

### 4.3 무한 루프를 끊는 사건

| 감지한 사건 | 처리 | 다시 시작할 수 있는 근거 |
|---|---|---|
| 동일 업무·단계·입력 버전·오류가 시정 시도 후에도 반복되고 산출물 변화가 없음 | 기존 재작업 한도와 비교해 먼저 닿은 조건에서 ‘확인 필요’. 반복 질문·위임·재계획 정지 | 새 원본, 다른 권한·도구, 구체적인 수정 지시 |
| 업무 A가 B를 기다리고 B가 다시 A를 요구 | 접수 시 순환 거부. 실행 중 발견하면 두 건의 의존 사유 표시 | 운영자가 선행 조건 수정 |
| 서버 중단 뒤 실행이 살아 있는지 불명확 | 기존 업무·시도와 결과 증거를 먼저 대조. 늦은 응답이 새 결과를 덮어쓰지 않게 함 | 실행되지 않았음이 확인된 단계, 또는 기존 결과로 완료 처리 |
| 결과는 확정됐는데 보고 카드 저장에 실패 | 동일 카드의 저장만 최초 1회 + 최대 재시도 2회 제안. 이후 화면에 보고 반영 실패 표시 | 기존 결과로 수동 복구. 업무 재실행 0회 |
| 갱신 이벤트·예약 회차·감시 자료가 중복 도착 | 동일 사건은 한 번 소비. 완료 이벤트는 새 업무 지시로 해석하지 않음 | 새 제출, 새 예약 회차, 새 자료 키 |
| 계정 장애·서비스 중단이 여러 업무에 반복 | 공통 장애가 확인되면 해당 연결을 쓰는 업무만 보류하고 같은 로그인을 재시도하지 않음 | 연결 복구를 확인한 뒤 한 건으로 검증하고 재개 |

### 4.4 운영자가 지연과 발송 결과를 확인하는 세 가지 기능

| 기능과 진입점 | 운영자의 행동과 결과 | 개발·검수 기준 |
|---|---|---|
| **업무 처리 이력 내보내기** · 묶음 보고의 ‘처리 이력’ | 다운로드 전에 업무별 접수 순서·시도·보류 사유·소요 시간·AI 사용량을 확인한다. 선택한 묶음의 이력을 UTF-8 CSV로 저장한다. 휴대폰에서는 같은 내용을 스레드 안에서도 읽을 수 있다. | 업무 번호·시도 번호·사건 번호로 접수, 시작, 보류, 재개, 완료를 연결한다. 시간은 한국 시각으로 표기한다. 건수는 업무 번호, 호출은 개별 호출 번호로 한 번씩 센다. 미보고 호출을 따로 표시한다. 기존 조회 권한을 적용하고 요청 원문·수신 주소·인증값은 내보내기에서 제외한다. 생성 시 AI 호출 0회. |
| **발송 결과 대조함** · ‘내 확인 필요’와 해당 업무 스레드 | 발송 직후 앱이 끊긴 건을 열어 승인된 문안 버전·대상·시도 시각과 보낸메일함 또는 게시 증표를 한 화면에서 맞춰 본다. | 증표가 일치하면 ‘발송 확인’으로 마감한다. 근거가 부족하면 ‘확인 보류’로 남겨 독립 업무를 진행한다. 미발송 근거 확인 후 권한 있는 운영자가 대상·문안을 확인하고 ‘새 발송 승인’을 선택해야 새 시도를 만들 수 있다. 대조·새로고침·다른 기기에서 열기는 외부 발송 0회. 결정자·시각·근거를 기록하고 이미 처리된 건에는 최신 상태를 표시한다. |
| **대기시간 누적 알림** · 업무함의 ‘오래 대기 중’ | 가장 오래 기다린 업무를 누르면 선행 업무, 대기 시작 시각, 다음 행동이 보인다. 예를 들어 ‘배너 이월 정리 · 실행 자리 대기 28분 · 앞선 업무는 상담사 데이터 수집’으로 표시한다. | 실행 자리 대기 구간만 누적하고 선행 결과 대기·사람 답변 대기·실제 작업 시간은 각각 보관한다. 대기 원인이 바뀌면 해당 구간을 마감한다. 상태·시간 기록으로 계산해 AI 호출 0회. 알림 열람이 순번이나 실행 상태를 바꾸지 않게 한다. |

**대기 알림 운영값.** 파일럿에서는 시간만 기록한다. 운영팀이 같은 작업 공간에서 업무 유형별 정상 대기시간 분포와 표본 수를 검토해 임계시간·최소 표본 수를 승인하면 앱 안에서 알린다. 동일 업무·동일 원인·같은 대기 구간은 모든 기기를 합쳐 한 번만 알린다. 읽음은 공유하고, 실제 재개 후 다시 대기한 경우에만 새 구간을 연다. 표본이 부족한 유형은 대기시간만 보여 준다.

## 5. Slack형 화면에서 운영자가 보는 것

예를 들어 대시보드에 **“운영 업무 4건 · 완료 3 · 확인 필요 1”**이 보이면, 바로 아래 **“프로필 검수 목록 — 담당자 명단 첨부”**를 눌러 해결할 수 있어야 한다. 카드 공개 범위와 첨부 접근권한은 기존 업무에서 상속한다. 이 버전의 Slack형 범위는 화면 탐색과 스레드 구성이다. 외부 메신저 발송은 별도 일정으로 다룬다.

### 5.1 화면 폭에 따른 배치

기기 이름보다 브라우저가 실제로 쓸 수 있는 너비를 우선한다. 아래 폭은 CSS 픽셀 기준의 설계 제안값이다. 태블릿 분할 화면, 휴대폰 가로 모드, PC 확대 보기에서도 같은 규칙을 적용한다.

| 가용 폭 | 기본 배치 | 업무 상세를 열고 돌아오는 방법 |
|---|---|---|
| **1,200px 이상 · 넓은 화면** | 왼쪽 탐색 / 중앙 목록 / 오른쪽 업무 스레드의 3열. 중앙에는 접수 순서와 보류 사유를 유지한다. | 행을 선택하면 오른쪽 내용만 바뀐다. 스레드를 닫으면 선택했던 행에 초점이 돌아온다. |
| **768~1,199px · 태블릿 중심** | 접을 수 있는 탐색 메뉴와 목록·스레드 2열. 긴 문안이나 산출물은 상세 전체 보기로 확장한다. | 터치 한 번으로 업무를 열고 ‘목록으로’ 돌아간다. 가로·세로 회전 시 선택 업무·첨부 상태·작성 중 답글을 보존한다. |
| **767px 이하 · 휴대폰·좁은 창** | 업무함 → 묶음 → 업무 스레드를 한 화면씩 연다. 묶음 합계와 ‘확인 필요’를 맨 위에, 업무별 결과와 다음 행동을 세로 카드에 배치한다. | 앱과 브라우저의 뒤로 가기 모두 이전 필터·목록 위치를 복원한다. ‘새 업무’는 목록, ‘이 업무에 답글’은 스레드에서만 노출한다. |

### 5.2 작은 화면에서도 끝낼 수 있어야 하는 업무

1. **네 건 접수.** 휴대폰에서는 업무 카드를 세로로 추가한다. 접힌 카드에도 제목·첨부 수·선행 업무를 표시한다. 드래그와 함께 ‘위로/아래로’ 동작을 제공하고, 전송 전 네 제목과 순서를 한 번에 확인한다. 업로드 실패는 해당 파일에서 다시 시도한다. 접수 응답을 받기 전에 연결이 끊기면 같은 제출 번호로 접수 여부부터 조회한다.
2. **확인 요청에 답변.** ‘내 확인 필요 1건’을 누르면 막힌 이유, 필요한 자료, 답변 입력이 먼저 보인다. 화면 키보드가 열려도 입력란·보내기 버튼을 사용할 수 있어야 한다. 회전이나 메뉴 이동 뒤에는 작성 중인 글을 복원한다. 다른 기기에서 이미 해결했다면 갱신된 결정과 결과를 보여 준다.
3. **발송 대조.** PC는 승인본과 증표를 좌우로, 휴대폰은 ‘승인된 문안 → 관측된 발송 결과 → 처리 결정’ 순서로 배치한다. 태블릿은 상세 전체 보기로 긴 문안을 확인할 수 있다. ‘발송 확인’과 ‘새 발송 승인’의 문구와 위치를 구분한다. 두 기기가 같은 건을 동시에 승인해도 서버에서 새 시도는 한 건만 생성한다.
4. **보고·이력 확인.** PC의 결과 표는 휴대폰에서 업무당 카드 한 장으로 바뀐다. 제목, 상태, 산출물 또는 미완료 사유를 먼저 보여 주고 단계 이력과 사용량은 펼쳐 본다. 긴 파일명은 상세에서 전체 이름을 읽을 수 있고, 파일 미리보기를 닫으면 같은 업무로 돌아온다. 휴대폰 파일 저장을 취소해도 보고는 그대로 열려 있다.

**조작·가독성 기준.** 터치 대상은 최소 44×44 CSS px을 프로젝트 목표로 삼는다. 상태는 색과 텍스트를 함께 제공하고, 마우스를 올려야만 보이는 동작에는 터치·키보드 진입점을 둔다. 확대 시 버튼과 문구가 겹치지 않아야 한다. 원본 표·문서의 가로 스크롤은 미리보기 안에서만 허용하고 대시보드 본문은 화면 폭에 맞춘다. 실시간 갱신이 읽는 위치나 입력 초점을 빼앗지 않게 한다.

**기기 접근 전제.** 모바일 파일럿은 해당 기기에서 권한을 갖고 동일한 AI-Office 서버에 접속할 수 있을 때 진행한다. PC 로컬 주소만 열어 둔 상태에서는 태블릿·휴대폰이 그 PC의 업무를 조회할 수 없다. 테스트망에서 로그인·세션 만료·재접속을 먼저 확인한다. 연결이 끊기면 ‘마지막 갱신 시각’과 ‘연결 끊김’을 표시하고, 재접속 후 서버의 최신 상태를 확인한 뒤 발송 승인과 업무 재개를 활성화한다.

### 5.3 업무 봇 사용 가이드

**가이드 홈의 첫 질문은 ‘어떤 일을 맡기시겠어요?’로 한다.** 봇 이름을 몰라도 ‘상담사 메일’, ‘프로필 검수’, ‘정책 갱신’ 등 익숙한 업무명으로 찾는다. 검색 결과에는 부서·봇 이름·맡길 수 있는 일 한 줄·대표 산출물을 표시한다. 전체 봇은 부서와 역할로 필터링할 수 있다. 왼쪽 메뉴, 새 업무 작성창의 ‘명령 예시 보기’, 업무 스레드의 담당 봇 이름에서 같은 가이드로 진입한다.

| 봇별 상세 항목 | 운영자가 확인할 내용 |
|---|---|
| 맡길 수 있는 일 | 대표 업무와 결과물, 유사한 다른 봇과의 역할 차이. 자동 배정되는 협업·검증 전용 봇에는 참여 조건과 결과를 요청할 주관 업무를 안내한다. |
| 시작 전에 준비할 것 | 필요한 파일·조회 기간·대상·연결 권한을 필수와 선택으로 나눈다. 예시에는 가상 자료를 사용한다. |
| 어떻게 일하는가 | 실제 고정 절차 또는 검증된 업무 사례 순서로 ‘누가 → 무엇을 확인 → 어디에 결과를 남기는지’를 적는다. 필요할 때만 거치는 검토, 사람에게 질문하는 조건과 재개 방법을 표시한다. |
| 어떻게 명령하는가 | 봇마다 복사 가능한 대표 요청과 기존 업무에 보낼 보완 답글을 제공한다. 바꿀 값은 [기간], [대상], [원하는 결과]처럼 표시한다. 협업 전용 봇의 예시는 해당 봇이 참여할 주관 업무에 보내는 문구로 작성한다. |
| 완료 확인과 다음 행동 | 스레드에서 확인할 결과 본문·파일·미리보기, 완료 판단 기준, 자료가 누락됐을 때의 조치를 설명한다. 발송·게시가 있는 업무는 준비 완료와 실제 전송 완료를 구별한다. |

**상세 페이지 예시 · 상담사관리부 메일담당**  
운영자가 ‘상담사 메일’을 검색하면 ‘활동 리포트 문안과 미리보기 준비’와 ‘준비한 메일 발송’을 구분해 보여준다. 준비 요청은 대상과 기간 확인 → 활동 자료 확보 → 대상별 문안·미리보기 확인 순서로 안내한다. 담당자에게 자료 보완을 요청하면 운영자는 기존 업무 스레드로 돌아와 답한다.

| 상황 | 운영자가 사용할 문구 | 기대 결과 |
|---|---|---|
| 새 업무 맡기기 | “[기간]에 해당하는 [대상 상담사]의 활동 리포트 메일 초안을 준비해 줘. 대상별 문안과 미리보기를 보여줘.” | 새 업무 작성창에 초안이 채워진다. 운영자가 값을 바꾸고 접수하면 건별 문안과 미리보기를 준비한다. |
| 기존 업무 보완하기 | “대상 명단을 첨부했어. 이 명단을 기준으로 작성 중이던 문안을 이어서 준비해 줘.” | 선택한 업무의 답글 초안에 들어간다. 운영자가 답글을 보내면 같은 업무 번호로 이어진다. |
| 실제 발송 확인하기 | “승인할 문안과 수신 대상을 다시 보여줘.” | 원래 업무의 미리보기와 대상을 확인한다. 실제 발송 단계에서는 기존 권한과 승인 조건을 적용한다. |

**화면 동작.** ‘예시 복사’는 문구만 복사한다. ‘새 업무에 사용’은 작성창에 예시를 넣고, 이미 작성한 내용이 있으면 새 항목으로 추가할지 선택하게 한다. ‘이 업무에 답글로 사용’은 원래 스레드에서 열었을 때만 제공한다. 봇별 담당 표시는 배정 참고 정보로 사용하며 접수·실행은 기존 비서실장 경로를 따른다. 가이드 열람·검색·복사·초안 채우기에는 AI 호출이나 외부 전송이 발생하지 않는다.

**기기별 탐색.** PC는 봇 목록과 상세를 나란히 표시한다. 태블릿은 상세를 넓혀 절차와 예시를 읽을 수 있게 하고, 휴대폰은 검색 결과 → 봇 상세 → 업무 작성 순으로 연다. ‘뒤로’ 이동 시 검색어·필터·목록 위치와 작성 중인 업무를 복원한다.

**운영 관리.** 조직에 등록된 봇 ID와 고정 절차 ID를 가이드에 연결한다. 봇 이름이 바뀌어도 링크를 유지하고 휴무·비활성 상태는 검색 결과에 표시한다. 운영 담당자는 봇 추가나 절차 변경 시 대상·예시·산출물을 확인하고 마지막 검토일을 기록한다. 관리자에게 가이드 누락 및 재검토 대상 목록을 제공하고, 미확인 예시는 준비 중으로 표시한다.

## 6. 파일럿과 도입 승인 기준

### 무엇을 측정할 것인가

| 지표 | 측정 방식 | 파일럿 통과 기준 |
|---|---|---|
| 운영자 개입 | 제출 후 다음 건을 시작시키기 위한 추가 지시 횟수. 자료·권한 결정은 별도 분류 | 정상 4건에서 다음 업무 시작 지시 0회 |
| 접수·처리 정합성 | 제출 묶음, 건별 번호, 실제 실행과 최종 상태를 대조 | 4건 접수·4건 설명, 누락·중복 업무 0, 묶음 보고 1개 |
| 대기·처리시간 | 접수→시작, 실제 작업, 사람 대기, 결과 확정→보고, 전체 묶음 완료를 각각 기록 | 앞 건이 사람 대기로 전환된 후 사람의 답 없이 다음 독립 건 시작. 장기 업무로 인한 정상 대기는 별도 표시 |
| 토큰과 품질 | 같은 4건을 기존 단건 4회와 2.0 묶음 1회로 반복 비교. 모델·원본·검토 기준 고정. 건별 호출 수·입출력·캐시·미보고율과 산출물 완결성 비교 | 접수·대기·보고 조립 추가 AI 0회. 필수 산출물·검수 유지. 증가분이 있으면 어느 단계 때문인지 확인한 뒤 확대 결정 |
| 이상 종료 | 시도 ID·마지막 진전·사용량을 기록해 반복 질문, 중복 실행, 승인 후 예산 초기화를 대조 | 동일 조건의 무진전 재호출 차단, 한도 소진 후 신규 AI 호출 0, 외부 중복 전송 0 |

기준선에는 정상 단건, 고정 절차, 사람 확인 필요, 대표 장기 업무를 포함한다. 처음에는 모의 자료로 같은 입력을 반복해 편차를 기록하고, 실제 업무 파일럿에서는 외부 발송 전 단계를 사용한다. 운영 담당자는 산출물의 누락과 화면 이해도를 확인하고, 개발 담당자는 실행·복구·계측 근거를 제출한다.

### 반드시 통과할 운영 리허설

1. **정상 접수.** A~D를 함께 제출하고 실행 중 E를 추가한다. A~E가 한 번씩 순서대로 시작하며 직원 4슬롯과 업무 1자리 규칙이 함께 성립한다.
2. **누락·중복.** 저장 실패, 저장 직후 응답 유실, 더블클릭, 재접속을 각각 재현한다. 저장 실패는 성공 표시 0건, 같은 제출 재전송은 원래 번호가 돌아온다.
3. **보류와 재개.** A 자료 누락, B는 A 의존, C·D는 독립으로 설정한다. C·D가 완료되고 A·B는 같은 질문을 재전송하지 않는다. 보완 시 기존 번호로 필요한 단계만 이어간다.
4. **복구와 전송.** 실행 중, 외부 반영 직후, 결과 확정 직후의 세 시점에서 중단한다. 발송 증표가 불명확하면 확인 필요, 결과가 확정됐으면 보고만 복구한다.
5. **예산 경합.** 잔여 호출 1회일 때 직원 둘이 동시에 요청한다. 최대 1회만 선점한다. 사용량 미보고·응답 지연·재시작 후에도 예산을 초기화하지 않는다.
6. **반복 반려.** 같은 외부 문안 형식 오류를 반복 반환한다. 자동 호출은 유한하게 끝나고 해당 묶음 안 다른 독립 건으로 진행한다. 오류 문안 외부 전송은 0건이다.
7. **예약·감시.** 수동 4건과 예약·감시가 겹쳐도 감시 부모가 자리를 독점하지 않는다. 한 예약 회차·동일 자료 키로 생기는 후속 업무는 최대 1건이다.
8. **기존 기능·전환.** 단건 지시와 답장, 일시정지·재개, 빠른 조회와 고정 절차, 외부 권한, 과거 산출물, 모바일·PC 탐색을 확인한다. 새 대기 업무가 있는 동안 업데이트·동기화가 자동으로 서버를 정지시키지 않아야 한다.

9. **업무 처리 이력 내보내기.** 완료 3건·확인 필요 1건과 재시도 1회를 포함한 묶음을 내려받는다. CSV의 고유 업무 4개, 재시도 이력, 호출·미보고 건수가 화면과 일치하고 금지된 원문·인증값이 없어야 한다.
10. **발송 결과 대조함.** 모의 발송 직후 응답을 끊고 PC와 휴대폰에서 같은 건을 연다. 증표만 확인하는 동안 전송 0회, 동시 결정은 한 번만 반영된다. 새 발송은 미발송 근거와 별도 승인이 있는 경우에만 새 시도 번호를 부여한다.
11. **대기시간 누적 알림.** 파일럿용 임계값으로 대기→사람 답변 대기→재개를 재현한다. 구간별 시간이 겹치지 않고 임계값을 넘긴 동일 구간의 알림은 1개다. 표본 미달은 시간만 표시한다.
12. **기기별 업무 완주.** 아래 각 화면에서 4건 접수→확인 필요 1건 답변→최종 보고→처리 이력 조회를 완료한다. 접근 권한이 같은 두 기기에서 표시한 업무 번호·순번·결과가 일치하고 화면 조회만으로 추가 AI 호출이 발생하지 않아야 한다.

13. **봇 가이드로 첫 업무 맡기기.** 활성 봇 목록과 상세 페이지를 ID로 대조해 누락 0건을 확인한다. 봇 이름을 모르는 운영자가 휴대폰에서 ‘상담사 메일’ 검색 → 준비·발송 구분 → 예시로 초안 작성 → 접수까지 완료해야 한다. 같은 스레드를 다시 열어 보완 예시를 사용해도 새 업무가 생기지 않아야 한다. 명시적 접수 전 생성된 업무 0건, 가이드 조회·복사로 인한 AI 호출·외부 발송 0건을 검수한다.
