# 1.0 ↔ 2.0 교차검증 (2026-11-25)

1.0 기준 코드(`main` `d4ef6a7`, 별도 폴더에 펼침)와 2.0 코드(`v2-dev`)를 같은 조건으로 나란히 돌린 결과다. 운영 중인 1.0(4777, `~/AIOffice`)과 대표가 보는 개발 서버(4790)는 건드리지 않았다. 가상 구성·가상 자료만 썼고 외부 발송은 없다.

## 1. 자동 검사

| 확인 | 1.0 기준 코드 | 2.0 코드 |
| --- | --- | --- |
| 전체 테스트(`npm run check`) | 663개 중 654 통과·실패 4·건너뜀 5 | 713개 중 704 통과·실패 4·건너뜀 5 |
| 실패 4건 | 이 PC의 환경 문제(심볼릭 링크 1, codex 인자 2, Codex 기본 모델 1) | 같은 4건 |
| **1.0 원본 테스트 663개를 2.0 코드에 그대로 실행** | — | 653 통과. 새 실패 1건은 "화면 탭 4개" 검사(2.0에서 탭 구성을 바꿔 의도한 차이) |

기존 테스트 가운데 2.0에서 고친 것은 화면 탭 이름 1건과 실행기 테스트의 추가분뿐이다.

## 2. 코드 대조

`dashboard/orchestrator.mjs`·`runner.mjs`·`lib/ai-judge.mjs`·`browser-work.mjs`·`schedules.mjs`·`continuous.mjs`의 변경 줄을 읽었다. 기존 경로의 동작이 달라진 곳은 두 가지이고 둘 다 의도한 변경이다.

- 업무 예산을 다 쓰면 새 AI 호출을 시작하지 않고 계속할지 묻는다(1.0은 병렬 단계가 한도를 넘겨 시작할 수 있었다).
- 같은 발송 문안 형식 오류가 고친 뒤에도 되풀이되면 자동 반려를 멈추고 묻는다.

나머지는 덧붙인 것이다(순번 접수표, 호출 원장, 묶음 예산, 대조함 결정 반영). 1.0에서 시작한 업무를 2.0이 이어 갈 때 예산 한도 값이 없어 멈출 수 있는지 확인했는데, 1.0도 같은 값을 저장하므로 해당 없다.

## 5. 찾은 문제와 조치

1. **2.0 화면의 "끝난 대화에 이어 말하기"가 실제로는 실패했다(고침).** 서버는 1.0·2.0 모두 끝난 업무에 답글을 받지 않는다("이미 완료된 업무는 새 작업으로 지시해 주세요"). 2.0 화면은 끝난 대화에서 답글을 보내게 돼 있어 보내기가 거부됐다. 가짜 실행기 검사에 끝난 대화에서 실제로 보내 보는 확인이 없어 놓쳤다. 조치: 끝난 대화에서 보낸 말은 그 결과를 이어받는 새 업무로 접수한다(`after`). 화면 검사에 실제로 보내는 확인을 넣었고, 실제 Claude로도 확인했다.
2. **가이드 검색창에 한글을 치면 글자가 두 번 들어감(고침, 같은 날 대표가 발견).** 자동 검사는 입력란이 갈아 끼워지지 않는 것까지만 본다.

## 6. 이번에 확인하지 못한 것

- 실제 메일·카페 글·댓글 발송과 ERP 조회(금지 범위). 발송 직전 확인, 발송 결과 대조는 모의 발송기로만 봤다.
- 실제 회사 구성(부서 10개·고정 절차 6개)에서의 동작. 가상 부서 2개·직원 4명으로만 돌렸다. 고정 절차·예약·상시 감시·Aside 직원은 실제로 돌리지 않았다.
- Codex 엔진(검증실 포함). 이 PC의 codex 관련 테스트 3건은 양쪽에서 똑같이 실패한다.
- 화면을 사람이 직접 쓰는 흐름(실제 한글 입력기, 실제 휴대폰·태블릿).
- 표본 수. 업무 종류마다 한 번씩만 돌려 편차를 모른다.
- 2.0에서 대기·답변 필요 건이 남은 채 1.0으로 되돌리는 경우.

## D. 처음에 남겼다가 다시 고친 것 (2026-11-25, 대표 요청)

| 남겼던 것 | 다시 확인한 결과 | 조치 |
| --- | --- | --- |
| 감시 후속 업무가 시작에 실패하면 다시 시도하지 않음 | 접수표가 "사용자가 멈춤"으로 보고돼 감시가 다시 전달하지 않았다. 접수 기록이 없어진 경우도 계속 기다렸다 | 대표가 취소한 건만 "사용자가 멈춤"으로 알리고, 시작 실패·기록 없음은 실패로 알려 다음 확인 때 다시 전달한다. 시작 전에 일시정지된 건은 "기다리는 중"으로 알려 같은 일을 새로 만들지 않는다 |
| 판별을 기다리는 사이(최대 15초) 일시정지가 오면 그 건은 시작됨 | 맞다. 실행이 아직 없어 일시정지가 그 건을 보지 못했다 | 준비 중인 건에 표시를 남기고 실행을 만들기 직전에 확인해 시작하지 않는다. "이어서 해줘"로 다시 차례를 받는다. 실제 Claude로 확인(묶음 접수 직후 일시정지 → 시작 0건 → 재개 후 두 건 완료) |
| 다른 업무 진행 중의 답장은 차례를 기다림 | 설계대로다(한 번에 한 건). 예약이 그동안 다음 회차를 건너뛰는 것도 "앞 회차가 안 끝났으면 건너뜀"이라는 기존 규칙과 같다. 다만 화면에는 답했는데도 "답변 필요"로만 보였다 | 순번은 그대로 두고, 대화에 내가 보낸 답글과 "진행 중인 업무가 끝나면 이어서 진행합니다"를 보여 준다 |
| 업데이트 명령이 대기 건을 많이 셈 | 감시 후속 접수표와, 대표 답을 기다리는 선행 업무에 걸린 건까지 셌다 | 그 둘은 세지 않는다 |
| 한 건 보내기에 서버 차원의 중복 방지가 없음 | 응답만 잃고 다시 보내면 두 번 접수될 수 있었다 | 화면이 제출 키를 붙이고 서버가 10분 동안 같은 키에 처음 결과를 돌려준다. 실제 Claude로 확인(같은 제출 두 번 → 업무 1건) |
| 입력 토큰이 실행마다 크게 다름 | 원인을 찾았다. Claude는 캐시로 읽은 입력을 따로 보고하는데 화면은 캐시가 아닌 부분(몇 토큰)만 "입력"으로 보여 줬다. 실제 입력은 업무 한 건에 수십만 토큰이다 | 캐시분까지 더한 전체 입력을 보여 준다(Codex는 이미 들어 있어 더하지 않는다). 실제 확인: 단순 보고서 한 건이 AI 호출 6회·입력 약 78만·출력 약 5,700 토큰 |

재현 테스트 6개 추가(전체 725개 중 716 통과, 실패 4는 기준선). 화면 검사 130개·예전 화면 검사 53개·리허설 1~13 통과, 1.0 원본 테스트 결과도 그대로다.

**그래도 남는 것**
- 감시 후속 업무의 시작이 계속 실패하면(도구가 로그아웃된 채로 둘 때) 확인 주기마다 실패한 접수 기록이 하나씩 쌓인다. 1.0도 주기마다 다시 시도했다. 내역 초기화로 지워진다.
- 토큰 기준 한도는 아직 없다. 위 실측값(단순 업무도 수십만 토큰)을 보고 대표가 정할 일이다.

## E. 이번에도 확인하지 못한 것

실제 메일·글·댓글 발송과 ERP 조회, Codex 엔진(독립검증실), 실제 회사 구성에서의 고정 절차·예약·상시 감시 실행, 사람이 직접 쓰는 화면 흐름(한글 입력기·실제 휴대폰), 반복 실행의 편차. 화면 로직 수정은 화면 검사 130개와 단위 테스트로만 확인했고, "입력하는 사이 상태가 바뀌는" 경우 자체를 재현하는 자동 검사는 없다.
