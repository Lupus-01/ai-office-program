# AI-Office 2.0 기획 검토 보고서

2026-11-25 · S0 산출물 · 기획 정본 [PLAN.md](PLAN.md) · 작업 순서 [WORK-PLAN.md](WORK-PLAN.md)

검토 기준 커밋은 `d4ef6a7`(PLAN이 적은 `9aa37ed`보다 4개 뒤)이다. 아래 "확인된 현행"은 이 커밋의 코드를 직접 읽어 확인한 것이고, 실제 Claude·Codex 실행으로 잰 값은 없다. 줄 번호는 이 커밋 기준이다.

## 결론

- PLAN의 진단 여섯 가지는 코드에서 모두 확인됐다. 틀린 진단은 없다.
- PLAN의 "기존 업무 보존 전략"(단건 실행은 그대로 두고 접수·순번·예산·보고를 바깥에 둔다)은 지금 구조에 맞는다. 상위 업무 실행이 직원 한도에서 이미 빠져 있어서, 순번 실행기는 `runner.start` 앞에 문 하나를 두는 형태로 넣을 수 있다.
- PLAN과 다른 점이 세 가지 있다(아래 1절). 그중 "다른 기기 접속"은 PLAN이 없다고 본 기능이 일부 이미 있다.
- 구현 전에 대표가 정할 것은 D1~D7이다(5절). S1은 D1만 있으면 시작할 수 있다.

PLAN의 서술과 코드가 다른 점:

1. **예산 기본값.** PLAN은 "업무당 240회·180분"이라고 적었는데 이는 회사 설정값이다. 프로그램 기본값은 40회·60분(`lib/guardrails.mjs` `DEFAULT_TASK_BUDGET`), 허용 범위는 5~500회·5~1440분이다. 개발용 작업 공간은 기본값으로 돈다.
2. **다른 기기 접속.** 서버는 `--host`로 이 PC 밖 주소에 열 수 있고, 그때는 일회 키를 쿠키로 바꾸는 인증(`dashboard/server.mjs` `authorizeRemote`)이 이미 동작한다. 다만 서버를 켤 때마다 바뀌는 공용 토큰 하나뿐이고(사용자 구분·세션 만료 없음), 암호화(HTTPS)가 없다. S10은 새로 만드는 일이 아니라 이 부분을 보강하는 일이다.
3. **업데이트의 진행 중 업무 확인.** `scripts/update.mjs`는 실행 목록의 `running`·`queued`만 센다. 2.0의 대기 순번은 실행 목록 밖에 저장되므로, 그대로 두면 대기 업무가 있어도 업데이트가 서버를 끈다(S3에서 고친다).

## 2. 확인된 현행 (PLAN "2. Evaluate" 여섯 지점)

| 지점 | 코드에서 확인한 것 | 판정 |
| --- | --- | --- |

| 계측 누락·중복 | 접수 판별과 답변 판별(`judgeAnswer`)은 `execute`를 거치지 않아 예산·사용량에 안 잡힌다. 자식 사용량은 부모 실행에 더한다(`runner.mjs` 700행) — 자식 실행에도 같은 값이 남는다. `addDailyUsage`는 보고되지 않은 토큰을 0으로 더한다. `addUsage`는 한쪽이 미보고면 그 항목의 합계를 null로 만든다 | PLAN과 같음. "미보고 호출 수"를 따로 세는 곳은 없다 |
| 재시작 정리 | `runner.mjs` `loadRuns`: `running`은 `failed`+"추적이 끊겼습니다"(상위 업무는 `interrupted` 표시), `queued`는 `stopped`로 바꾼다. 감시만 `restoreContinuous`로 되살린다. 예약은 놓친 시각을 건너뛴다(`lib/schedules.mjs`) | PLAN과 같음. 일반 대기 건은 재시작하면 사라진다 |

2.0 설계에 직접 걸리는 추가 사실:

- 실행 목록(`.office/runs.json`)은 200개까지만 남긴다. 처리 이력·묶음 보고가 실행 목록에 기대면 오래된 묶음의 이력이 사라진다. 묶음 저장소가 스스로 사건 기록을 가져야 한다.
- 감시가 만든 후속 업무(`runner.mjs` 750행 `dispatch`)와 예약 회차(`createSchedules({ start })`)는 `runner.start`를 직접 부른다. 순번 실행기를 두면 이 두 곳도 같은 문을 지나게 바꿔야 한다(S3).
- 지시창의 일시정지·재개·추가 지시·예약 등록·내역 정리는 판별 결과로 갈린다. 이 길은 순번 대기열과 무관하게 즉시 처리돼야 한다(5절 D2).

PLAN의 요청 항목 가운데 보고서 본문으로 따로 답할 것:

- **단건과 4건 묶음의 차이(같은 사례).** 지금 A~D를 지시창에 차례로 넣으면 넷이 거의 동시에 시작된다(상위 업무 수에 상한이 없다). 판별 4회가 접수 전에 나가고, 네 업무의 단계가 직원 4자리를 두고 섞인다. B는 A의 집계를 기다리지 않고 스스로 조사한다. 2.0에서는 저장만 하고(판별 0회) A부터 한 건씩 시작하며, B는 A의 확정 산출물 경로를 입력으로 받는다.
- **다음 독립 업무가 시작되는 조건.** 실행 중인 건이 완료·질문 대기(`needsReply`)·실패·중지·예산 보류 중 하나가 되면 자리를 비운다. 지금 코드에서 이 다섯은 모두 상위 실행이 끝나는 한 지점(`runner.mjs` 767~773행)을 지나므로, 순번 실행기는 그 지점의 알림 하나만 들으면 된다.
- **비용이 생기는 주체.** 접수·순번·보고·이력·가이드는 서버 코드만 돈다. AI 비용은 실행 차례가 온 건의 판별 1회와 그 건의 계획·단계·점검·검토에서만 생긴다.
- **화면에서 기존 기능이 옮겨지는 곳.** 관제 → 업무함(중앙 목록), 대화·승인·메일 미리보기·파일 받기 → 오른쪽 스레드, 사무실·조직·산출물 → 보조 메뉴, 예약·계정 연결·회사 설정 → 관리 메뉴. 없애는 기능은 없다.

## 4. 검증 방법

- 단계마다 `npm run check` 전체에서 새 실패 0. 기준선은 663개 중 654 통과·실패 4(환경 문제, [PROGRESS.md](PROGRESS.md))이고 이 폴더에서 다시 재서 1.0과 같음을 확인했다.
- 리허설 1~13은 가짜 실행기(`spawnImpl` 교체)와 모의 발송기로 자동화한다. "AI 호출 0회" 구간은 가짜 실행기의 호출 수로, "외부 발송 0회"는 모의 발송기의 기록 수로 단언한다.
- 화면은 `scripts/verify-ui.mjs` 방식으로 폭별 브라우저 검사를 한다. 실제 기기 검증은 S10 뒤 따로 기록한다.
- 실제 Claude·Codex로 재는 것(토큰·시간 기준선, 4건 비교)은 S11에서만 하고, 외부 발송 전 단계까지만 쓴다.

지금 확인하지 못한 것: 실제 운영에서의 호출 수·토큰·대기시간(코드로는 알 수 없음), 회사 구성의 고정 절차 6개·예약 4건의 현재 내용(`company-data` 브랜치를 이번에는 펼치지 않았다 — S9에서 읽는다).
