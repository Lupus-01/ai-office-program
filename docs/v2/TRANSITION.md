두 서버는 프로그램 폴더·작업 공간·포트가 모두 달라 서로의 파일을 건드리지 않는다(확인함: 2.0 개발 내내 4777이 응답했다).

## 2.0이 작업 공간에 새로 쓰는 것

- `.office/batches/<묶음 번호>.json`, `.office/batches/<묶음 번호>.report.json` — 접수 묶음과 보고 카드
- `.office/ledger/` — AI 호출 원장
- `org/guides.json` — 업무 예시(사람이 관리하는 파일, 프로그램은 읽기만 한다)
- 브라우저에만: 대화별 쓰던 글, 읽음 표시, 고른 대화, 거르기

기존 파일(업무·실행 기록·산출물·조직·예약·계정)의 형식은 바꾸지 않았다. 지시창 한 건도 "한 건짜리 묶음"으로 접수되므로 2.0으로 돌린 업무에는 묶음 파일이 함께 생긴다.

## 병행 단계 (권장 순서)

1. **리허설 결과표 확인** — `npm run rehearsal`(가짜 실행기). 2026-11-25 기준 1~13 통과. 12의 실제 기기 행은 S10 뒤.
2. **실측** — 개발용 작업 공간(가상 구성)에서 실제 Claude로 외부 발송 없는 업무를 보내 체감 속도와 호출 수·토큰을 잰다. 아직 하지 않았다. 토큰 기준 한도(기획 4.2)는 이 값을 보고 정한다.
3. **내부 파일럿(D7)** — 외부 발송 없는 업무 4건. 실제 작업 공간의 **복사본**에 2.0을 붙여 돌린다(`--workspace <복사본> --port 4790`). 실제 `~/AIOffice`에는 붙이지 않는다. 계정 연결·발송은 쓰지 않는다.
4. **전환** — 대표가 정한 날 1.0 서버를 끄고, `~/AIOffice`를 통째로 백업한 뒤 2.0을 그 작업 공간에 붙인다. 한 작업 공간에 1.0과 2.0 서버를 동시에 붙이지 않는다.

## 되돌리기 (2.0 → 1.0)

1. 2.0 대화 화면에서 새 업무를 보내지 않는다. 진행 중인 업무가 끝나길 기다리거나 중지한다(`npm run office:stop`은 실행 중인 AI 작업도 정리한다).
2. 보존 확인: 완료 결과(`outputs/`, `보관함/최종산출물/`), 대기 순번(`.office/batches/`), 발송 증표(`.office/publications/`).
3. 2.0 서버를 끄고 1.0 프로그램 폴더에서 같은 작업 공간으로 서버를 켠다.
4. 1.0은 `.office/batches/`·`.office/ledger/`·`org/guides.json`을 모른다. **차례를 기다리던 건은 1.0에서 스스로 시작되지 않는다** — 필요한 건은 1.0 지시창에 다시 지시한다. 이미 끝난 업무와 산출물은 1.0 화면에서도 보인다.

## 확인 못 한 것 (전환 전에 확인)

- **1.0이 2.0이 쓴 작업 공간을 읽어도 안전한지.** 형식을 바꾸지 않았다는 것은 코드로 알지만, 1.0 프로그램으로 2.0이 쓴 작업 공간을 실제로 열어 보지는 않았다(1.0은 건드리지 않기로 했다, D8). 작업 공간 복사본으로 확인해야 한다.
- 2.0에서 묶음으로 접수돼 "답변 필요"로 멈춘 업무에 1.0에서 답장했을 때의 동작(1.0에는 순번 실행기가 없다).
- 실제 Claude·Codex로 돌린 2.0 흐름 전체. 지금까지의 검증은 모두 가짜 실행기·가짜 CLI·모의 발송기다.
- 실제 메일·Aside·브라우저 경로의 발송 결과 대조(공식 API 자리의 모의 발송기로만 봤다).
- 받아 쓰는 PC(공유 회사 구성)에 2.0을 배포하는 길. `v2-dev`는 `main`에 합치지 않았고 `office:update`는 `main` 계열을 받는다.
