# AI-Office 2.0 작업 계획 (세션 단위)

기획 정본은 [PLAN.md](PLAN.md)(운영 기획서, 2026-11-24)다. 이 문서는 그 기획을 **세션 하나에 끝낼 수 있는 크기**로 나눈 작업 순서다. 진행 상태는 [PROGRESS.md](PROGRESS.md)에만 적는다(이 문서는 계획이 바뀔 때만 고친다).

## 0. 모든 세션이 지키는 것

### 시작할 때

1. `docs/v2/PROGRESS.md`를 읽고 "다음 세션이 할 일"의 단계 하나만 맡는다. 한 세션에 두 단계를 하지 않는다.
2. 그 단계가 가리키는 `PLAN.md` 절과 아래 단계 설명을 읽는다. `docs/SPEC.md`는 고칠 주제의 절만 읽는다(전체 832줄을 다 읽지 않는다).
3. `git status --short && git log --oneline -3`으로 깨끗한지 본다. 커밋되지 않은 변경이 있으면 PROGRESS의 "진행 중 메모"와 대조하고, 설명이 없으면 대표에게 묻는다.

- 외부로 나가는 동작(메일·카페 글·댓글·ERP 조회)은 2.0 개발에서 실행하지 않는다. 가짜 실행기·모의 발송으로만 검증한다.

### 설계 원칙 (PLAN의 "기존 업무 보존 전략")

- 단건 업무의 분담·검토·권한·결과 전달(`dashboard/orchestrator.mjs`)은 **재사용**한다. 접수 순서·예산·묶음 보고는 그 **바깥**(접수 저장소와 순번 실행기)에 둔다.
- 새 동작은 기존 단건 지시·답장·예약·감시·고정 절차를 깨지 않아야 한다. 단계마다 기존 테스트 전체가 그대로 통과해야 한다(이 PC의 기존 환경 실패 4건 제외: 심볼릭 링크 1, codex 2, "비서실장 기본 Codex sol 6.1 max" 1).
- 접수·순번·화면 갱신·보고 조립·이력 내보내기·가이드는 **AI 호출 0회**다. 테스트에서 가짜 실행기의 호출 수로 확인한다.
- 상태 전이는 한 곳(순번 실행기)에서만 일어나게 한다. 화면 조회·재접속·중복 이벤트가 업무를 시작시키면 안 된다.

### 끝낼 때

1. `npm run check` 결과(전체 수·통과·실패 이름)를 PROGRESS에 적는다. 새 실패가 있으면 끝내지 않는다.
2. `docs/SPEC.md`의 해당 절과 `docs/DECISIONS.md`(결정이 있었으면)를 고친다.
3. 커밋(작은 단위, 한국어 메시지) → `git push origin v2-dev`.
4. PROGRESS의 단계 표·"다음 세션이 할 일"·"대표 결정 대기"를 갱신하고 그것도 커밋·push한다.
5. 대표에게는 한국어로, 한 것·확인한 것·확인 못 한 것·정해 줄 것만 짧게 보고한다.

### 컨텍스트 관리

- 큰 파일(`app.js` 3,774줄, `server.mjs` 1,757줄, `orchestrator.mjs` 1,221줄, `runner.mjs` 1,015줄)은 통째로 읽지 않는다. Grep으로 위치를 찾고 필요한 범위만 읽는다.
- 컨텍스트 압축이 한 번 일어나면 그 단계의 다음 커밋 지점에서 PROGRESS에 "진행 중 메모"를 남기고 세션을 끝낸다. 압축된 채로 다음 단계로 넘어가지 않는다.
- 조사만 하는 넓은 탐색은 하위 에이전트에 맡기고 결론만 받는다.

### S0 — 환경 준비와 기획 검토 보고서

PLAN의 마지막 절은 "이번 요청의 완료 지점은 기획 검토 보고서 제출, 구현 착수는 별도 승인"이라고 적혀 있다. 대표가 2026-11-25에 2.0 작업 진행을 지시했으므로 S0에서 검토 보고서를 내고, **S1 착수 전에 대표에게 한 번 확인**받는다.

할 일:
1. `npm ci` → `npm run check`로 기준선을 잰다(영문 경로에서 직접). 1.0에서 재던 수치(663개 중 654 통과·실패 4)와 다르면 원인을 적는다.
2. 개발용 작업 공간을 만든다: `node dashboard/server.mjs --workspace C:\Dev\ai-office-2.0-workspace --port 4790`이 뜨는지 확인하고 끈다. 가짜 부서 2개·직원 4명 정도의 구성을 넣는다(실제 회사 구성을 복사하지 않는다).
3. PLAN의 기준 커밋 `9aa37ed` 이후 바뀐 것을 `git log 9aa37ed..HEAD`로 읽고, PLAN "1. Read"의 표와 달라진 동작을 적는다. 이미 아는 차이: 고정 절차 담당이 Aside 직원이면 절차를 쓰지 않음, Aside 전환 권장에서 절차 담당 제외, 상담사관리 수집 도구 공유.
4. PLAN "2. Evaluate"의 여섯 지점을 코드에서 다시 찾아 파일·함수 이름과 함께 확인한다(접수 전 의도 판별 `lib/ai-judge.mjs`·`lib/intent.mjs`, 직원 대기열 `dashboard/runner.mjs`의 `maxConcurrent`, 검토·형식 오류 왕복과 예산 `dashboard/orchestrator.mjs`·`lib/guardrails.mjs`, 사용량 합산 `lib/usage.mjs`, 재시작 정리 `dashboard/server.mjs`·`runner.mjs`).
5. `docs/v2/REVIEW.md`를 쓴다. 형식은 PLAN이 요구한 "확인된 현행 / 2.0 제안 / 운영자가 결정할 값 / 검증 방법"이다. 길게 쓰지 않는다. 단계 S1~S11마다 고칠 파일과 새 파일, 저장 형식 초안, 위험을 한 표로 정리한다.
6. 아래 3절의 결정 목록을 대표에게 한 번에 묻고 답을 PROGRESS "대표 결정"에 적는다.

끝난 기준: 기준선 수치, REVIEW.md, 결정 답, S1 착수 확인.

### S1 — 접수 저장소

- 새 모듈(예: `lib/batches.mjs`)과 저장 위치(작업 공간 `.office/batches/`). 묶음 번호, 건별 번호, 제출 순번, 항목별 요청 원문·첨부·완료 기준·선행 업무, 제출 키.
- API: 묶음 제출(전체를 저장한 뒤에만 접수 완료 응답), 묶음·건 조회. 같은 제출 키로 다시 보내면 같은 번호를 돌려준다. 저장 실패면 성공 표시 0건.
- 선행 업무는 같은 묶음의 앞선 항목만 고를 수 있게 해 순환을 막는다.
- 이 단계에서는 실행하지 않는다(저장과 조회만). 접수에 AI 호출 0회.
- 통과: 리허설 2(저장 실패, 응답 유실 뒤 재전송, 더블클릭, 재접속).

### S2 — 순번 실행기

- 같은 작업 공간에서 "실행 가능한 건 중 가장 먼저 접수된 건" 하나를 골라 기존 단건 실행(`runner.start` → `orchestrate`)에 넘긴다. 상위 업무 자리(1)와 직원 자리(`maxConcurrent` 4)를 따로 센다.
- 답변·자료·승인·예산을 기다리는 건, 실패한 건은 자리를 반납하고 다음 독립 건을 시작한다. 선행 결과가 필요한 건은 사유를 달아 보류한다.
- 실행 중 추가 접수, 보류 건 보완 시 같은 번호로 재개(같은 답장 반복은 한 번만), 사람이 중지한 건은 명시적 재개 전까지 멈춤.
- 의도 판별은 실행 차례에 한 번만 하고 결과를 건에 저장한다.
- 기존 지시창의 단건 지시는 "한 건짜리 묶음"으로 같은 길을 타게 할지, 기존 길을 그대로 둘지 REVIEW의 결정에 따른다.
- 통과: 리허설 1(A~D 제출 후 E 추가), 3(A 자료 누락·B는 A 의존·C·D 독립).

### S3 — 복구와 중복 방지

- 서버 재시작 뒤 대기 순번을 저장된 정보로 복구한다. 실행 중이던 건은 결과 증거를 먼저 대조하고, 늦게 온 응답이 새 결과를 덮어쓰지 않게 한다.
- 완료 이벤트·화면 갱신·예약 회차·감시 자료의 중복 도착은 한 번만 소비한다. 완료 이벤트를 새 지시로 해석하지 않는다.
- 유한 예약은 회차당 한 번만 접수하고, 상시 감시 부모는 상위 업무 자리를 차지하지 않는다. 감시에서 나온 유한 후속 업무만 같은 대기열을 쓴다.
- 대기 업무가 있는 동안 업데이트·동기화가 서버를 자동으로 끄지 않게 한다(1.0에서 실행 중 재시작으로 예약 업무가 끊긴 적이 있다).
- 통과: 리허설 4(실행 중·결과 확정 직후 중단), 7, 8의 서버 쪽.

### S4 — 계측과 예산

- 공급자 호출마다 번호를 붙여 한 번만 세는 원장. 판별 호출처럼 지금 업무 예산 밖에 있는 호출도 넣는다. 부모 합계와 자식 호출은 한쪽만 합산한다.
- 업무 예산과 묶음 예산 두 층. 병렬 직원 호출은 시작 전에 잔량을 선점하고 끝난 뒤 실측으로 정산한다. 80%에서 한 번 알림, 100%에서 새 AI 호출 0.
- 미보고 사용량은 0으로 정산하지 않고 "확인된 입력·출력 / 미보고 호출 수 / 측정 가능 비율"로 표시한다.
- 같은 업무·단계·입력 버전·오류가 고친 뒤에도 되풀이되고 산출물 변화가 없으면 "확인 필요"로 보류한다. 외부 전송 조건 미충족을 자동 승인으로 풀지 않는다.
- 통과: 리허설 5(잔여 1회에 직원 둘), 6(같은 형식 오류 반복).

### S5 — 묶음 보고, 처리 이력, 대기시간

- 묶음 보고 카드: 건별 번호·제목·상태·결과 한 줄·산출물 또는 미처리 사유·다음 행동. 상태별 건수 합계는 항상 최초 접수 건수와 같다. 보고 저장 실패는 최초 1회 + 재시도 2회, 그 뒤 "보고 반영 실패" 표시(업무 재실행 0회).
- 처리 이력 UTF-8 CSV: 업무 번호·시도 번호·사건 번호로 접수·시작·보류·재개·완료를 잇는다. 한국 시각. 요청 원문·수신 주소·인증값은 내보내지 않는다.
- 대기시간: 실행 자리 대기, 선행 결과 대기, 사람 답변 대기, 실제 작업 시간을 겹치지 않게 따로 기록한다. 알림은 값이 승인되기 전에는 기록만 한다.
- 통과: 리허설 9, 11.

### S6 — 발송 결과 대조함

- 발송 직후 끊긴 건을 승인된 문안 버전·대상·시도 시각과 발송 증표로 한 화면에서 맞춰 본다. 대조·새로고침·다른 기기에서 열기는 외부 발송 0회.
- "발송 확인"과 "새 발송 승인"을 구분하고, 두 기기가 동시에 승인해도 서버에서 새 시도는 한 건만 만든다. 결정자·시각·근거를 기록한다.
- 모의 발송기로만 검증한다(실제 메일·게시 금지).
- 통과: 리허설 10, 4의 "외부 반영 직후 중단".

### S7 — 화면 1: 업무함 (넓은 화면)

- 왼쪽 탐색(업무함·내 확인 필요·최종 보고·업무 봇 가이드) / 중앙 목록 / 오른쪽 스레드. 기존 관제·사무실·조직·산출물은 보조·관리 메뉴로 옮긴다(없애지 않는다).
- "새 업무": 항목을 하나씩 추가, 항목별 원문·첨부·완료 기준·선행 업무, 전송 전 제목·순서 확인.
- 실시간 갱신이 읽는 위치와 입력 초점을 빼앗지 않게 한다. 화면 조회만으로 AI 호출이 생기지 않는지 확인한다.
- 화면 확인은 `scripts/verify-ui.mjs` 방식(가짜 실행기 + 브라우저)으로 자동화한다.
- 통과: 리허설 12의 PC(1440×900, 확대 200%).

### S8 — 화면 2: 태블릿·휴대폰

- 768~1,199px 2열, 767px 이하 한 화면씩. 뒤로 가기 시 필터·목록 위치·작성 중 답글 복원, 회전 시 선택 업무·첨부 상태 유지.
- 터치 대상 44×44 CSS px, 상태는 색과 글자를 함께, 대시보드 본문 가로 넘침 0.
- 통과: 리허설 12의 모의 폭(768×1024, 1024×768, 360×800, 390×844).

### S9 — 업무 봇 사용 가이드

- 조직의 봇 id와 고정 절차 id에 연결된 가이드 목록·상세(맡길 수 있는 일, 준비물, 처리 순서, 복사할 명령 예시, 완료 확인). 검색은 업무 이름으로.
- "예시 복사", "새 업무에 사용", "이 업무에 답글로 사용". 열람·검색·복사·초안 채우기는 AI 호출·외부 전송 0.
- 가이드 내용은 회사 데이터다. 프로그램에는 형식과 화면만 넣고, 실제 문구는 작업 공간 파일로 둔다(공개될 수 있는 코드에 회사 업무 문구를 넣지 않는다).
- 통과: 리허설 13.

### S10 — 다른 기기 접속

- 지금 서버는 이 PC(127.0.0.1)에서만 열린다. 태블릿·휴대폰이 보려면 서버를 밖에 열어야 하고, 이는 회사 업무 화면을 네트워크에 내놓는 일이다. **접속 방식은 대표가 정한다**(3절 D4). 정해지기 전에는 구현하지 않고 S8까지의 모의 폭 검증으로 둔다.
- 로그인·세션 만료·재접속, "마지막 갱신 시각"·"연결 끊김" 표시, 재접속 뒤 최신 상태를 확인하고 나서야 승인·재개 버튼을 켠다.
- 통과: 리허설 12의 실제 기기 행.

### S11 — 전체 리허설과 전환

- 리허설 1~13을 한 번에 돌리는 스크립트와 결과표. 기준선 측정(정상 단건, 고정 절차, 사람 확인 필요, 장기 업무)을 같은 입력으로 반복해 편차를 적는다.
- 1.0과 병행하는 방법, 되돌리는 방법(신규 선점 정지 → 완료 결과·대기 순번·외부 증표 보존 → 단건 운영 복귀), 구버전이 새 상태 파일을 읽어도 안전한지 확인.
- 실제 업무 파일럿은 외부 발송 전 단계까지만. 시작 여부는 대표가 증빙을 보고 정한다.
